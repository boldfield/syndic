CONSENSUS HARNESS — DESIGN CANDIDATE v2
Codex, 2026-10-08. Review this exact candidate and both peers' complete preceding responses. State approve, block, or approve-with-changes; address your peer directly. No code implementation is requested.

1. Product contract
A local personal chat/coding TUI routes every request through a policy checkpoint. It offers solo, review, and deliberate protocols. Review is the initial default. Solo is explicit or a narrowly configured fast path; deliberate is for alternatives and architecture. Depth, resource ceilings, and effect authorization are separate controls. Consensus is agreement, never proof of correctness.

2. Protocols
Solo: one answer, visibly unreviewed. Review: proposer creates a candidate; independent reviewer receives full request, evidence and exact candidate; accept or bounded revision followed by re-review. Deliberate: independent proposals from all participants; every participant receives all complete peer proposals; one full peer-critique round; a designated integrator creates one candidate and objection disposition list; required reviewers inspect that exact candidate. The integrator cannot approve its own candidate. In three-participant deliberation the other two approve; the integrator records authorship, not a third independent vote. Required participants are declared before dispatch. A new material objection can trigger one repair round within budget; otherwise return dissent/incomplete. Terminal verdicts are shared with all participants without recursively requiring replies to acknowledgments.

3. Delivery and context
Immutable messages include session, turn, phase, sender, recipient set, sequence, content hash, byte length, and parent IDs. Hashes are computed by the engine, not the model. Retrying the same message ID is idempotent; identical content from different senders is legal. Validate before dispatch; persist provider submission receipts when supported. A model saying it received a message is not proof of complete context. Never summarize or truncate active-turn peer messages. If output exceeds budget, preserve it and stop or request an explicitly superseding authored replacement. Do not silently cut it. Context overflow stops the turn or starts a human-approved split. Provider hidden compaction is reported unknown/unsupported; no promise of verified attention or complete internal retention. Historical compaction retains originals and a manifest of omissions.

4. Verdicts and objections
Candidate identity covers exact answer bytes or patch plus base/tree manifest, test artifacts, relevant evidence, policy version and required reviewer roster. Any relevant mutation invalidates approvals. approve-with-changes is a revision request, not approval. Blocks carry IDs, severity, evidence and a requested remedy; they survive revisions until their reviewer withdraws them against the new candidate or the human explicitly overrides. Overrides are labeled HUMAN OVERRIDE, never CONSENSUS. Different vendors/models improve diversity but do not prove statistical independence.

5. Routing and defaults
Log requested and observed capabilities, unknown scope, protected paths, destructive/external operations, and policy rule. Any write/command intent requires at least review; ambiguous requests stay reviewed. Recheck before tools and final release. No prompt-length score or model confidence threshold claims to measure complexity. Fabel and Muse prefer wider output-checked solo to reduce latency. Codex objects that plain prose can advise disabling authentication without code or tools, so scanning is no assurance boundary. Preserve this dissent: ship strict default and an explicitly selected quick profile; scanners may escalate, never certify safety. Tune with measured false negatives, caught defects, latency, quota consumption and bypass rate, not an invented target percentage of solo turns.

6. UI and budgets
Primary pane shows the reviewed answer; a status strip shows protocol, phase, elapsed time, provider/auth mode and approvals. Tabs expose full participant messages, evidence, patch and dissent. Drafts are opt-in and marked unreviewed. Commands: /mode, /participants, /budget, /transcript, /why, /resume, /cancel. Steering creates a new input revision; relevant changes invalidate outstanding verdicts. A preset has provider/model roles, required roster, max rounds, per-phase deadline, output/context budgets and API spending ceiling. One local concurrency slot per provider initially. Deadlines are configurable and calibrated by pilot measurements, not latency promises. Missing required reviews, quota exhaustion, parser failure and interrupted output mean INCOMPLETE. Wait, explicitly substitute and restart affected review, or override; never silently drop a reviewer or switch to paid API.

7. Engine and persistence
A single local engine owns SQLite transactional state and an append-only event journal; TUI renders state. Large immutable artifacts live in a local content-addressed directory. Provider session IDs are resumable caches. Each attempt has an epoch so late output from cancelled/replaced attempts cannot approve current work. Durable intent precedes dispatch/effects; completion follows observed result. An uncertain inference may be retried with a recorded duplicate-compute risk, but an uncertain external effect is never replayed automatically. On crash, suspect worktrees/artifacts are quarantined for reconciliation and re-review. An API with verified idempotency can be queried/retried under that contract; otherwise a human reconciles. Test plans cover crash boundaries and replay, not only happy-path consensus.

8. Coding and Odonian
Discussion workers have no write/exec tools by default. An execution backend assigns exactly one writer per work unit to an isolated checkout at a frozen base; reviewers inspect frozen patch and independently obtained test artifacts. A worktree is not a sandbox: filesystem and subprocess network capabilities require OS/process enforcement. Model-provider network access must remain possible through a controlled channel while arbitrary tool egress is denied. Repository hooks/config/plugins are untrusted inputs. Review workers start in a clean controlled working directory with sanitized configuration and supplied snapshots, rather than launching in an untrusted project directory. Exact provider controls must pass contract tests before enabling review against repositories.
For this user, accepted design -> Odonian Project/Document/Tasks -> Haiku-sized initial implementation with escalation enabled -> independent reviews -> human merge. This harness is not a replacement Odonian scheduler. Local executor can be a later backend. No application code or fleet work is launched by this design exercise.

9. Adapters and subscription use
Priority: Codex App Server with provider-managed ChatGPT login; Claude Code structured noninteractive transport with provider-managed subscription login; manual courier for Muse; optional paid API adapters under explicit budgets. Avoid scraping rendered TUIs as the protocol and extracting browser cookies/tokens. Adapter capabilities include auth billing mode, version, stream completion, cancellation, session resume, structured output, tool restrictions, read isolation, context observability, and usage availability. Unknown quota stays unknown. Auth checks and live version probes precede each supported adapter release.
Official docs checked today support Codex subscription login and App Server controls, and Claude -p/SDK subscription usage. They do not prove this custom adapter works. Fabel found Claude bare mode skips subscription credentials while non-bare print mode can auto-run repo hooks/MCP. Therefore a clean-room subscription reviewer is a release blocker to resolve in the first spike, not a guessed flag. Codex documents readOnly sandbox and approvalPolicy never; these are separate controls and never does not itself mean no tools. Runtime sandbox behavior still needs testing. No verified Muse headless subscription transport exists in this investigation; manual courier is the MVP contract. API support is optional, not automatic failover.

10. MVP and evaluation
Gate A: subscription adapter feasibility, clean-room startup, reliable completion/cancel and auth-mode evidence. Gate B: durable review protocol and manual participant, text only. Gate C: deliberate all-to-all protocol and TUI. Gate D: Odonian handoff and artifact binding. Do not select Rust/Go/TypeScript based on preference alone; choose after the adapter spike demonstrates the smallest stable integration. Compare solo, review and deliberate on the same representative tasks with human-adjudicated quality, p50/p95 latency, output/usage, false approvals, reviewer-added defects, unresolved rate and user interruption rate. Accept only if transport mutation/duplicate/missing messages, stale verdicts, ignored blocks, timeout-as-approval, crash replay and unexpected paid fallback are covered by deterministic failure tests. No claimed quality gain until measured.


11. Required clarifications adopted after peer review
These clauses resolve the requested changes to v1 and govern where more specific.

Delivery verification: verify the exact serialized payload handed to the adapter, with hash and byte length, and compare receiver-side readback when the transport exposes it. Record constructed, submitted, readback-verified, or readback-unavailable separately. No provider-side retention or model-attention guarantee follows. An adapter cannot invent a readback receipt; the selected policy must explicitly allow an unavailable/attested transport. Replay identity is message ID plus sender/phase, not content hash alone: two peers may legitimately send identical text. Conflicting payloads under one ID are rejected; hashes and lengths must match expected bytes.

Manual courier: imported output is labeled courier-attested, never provider-verified. It is advisory by default; a user may explicitly require it before dispatch and accept the human latency/deadline. Advisory responses must arrive before candidate freeze to affect that candidate; later material objections create a new revision. Advisory must not be displayed as an independent required approval. Full-transcript deliberation requires all declared proposal participants to complete the proposal/critique exchange; missing ones yield INCOMPLETE, unless the user explicitly starts a new run with a changed roster. No silent roster shrinkage.

Quick profile: selectable once per project or per session, visibly persistent, with protocol default, eligible request categories, protected-path rules, required review triggers, output escalation rules, budget, and draft-display preference. Unknown/ambiguous scope still reviews. Scanners only escalate. The user can explicitly choose solo within effect restrictions; quick mode never changes sandbox permissions, mandatory human merge or spending authorization. No claim that any scanner detects all dangerous prose.

Test provenance: for a backend the harness owns, its separate sandboxed validation runner executes tests on the frozen candidate tree and records commands, exit status, environment identity, candidate hash and output hashes. Reviewers receive these artifacts without exec permission. Writer-reported logs are additional evidence. For the Odonian backend, consume evidence under its review contract and label provenance accurately; do not claim an independent rerun unless one occurred. If the required provenance is unavailable, stop that acceptance gate.

Provider startup: clean-room subscription review is a release blocker for BOTH automated adapters. Claude must use a verified version-specific configuration that preserves non-bare subscription behavior and fails closed on wrong/unknown billing mode; no unverified --no-bare flag is specified. Pin supported versions and detect changed defaults. Codex read-only, approval policy, hook/plugin/MCP suppression, read boundaries and tool egress all need contract tests. Authentication self-tests can verify behavior, not provider policy permission; maintain dated official-document evidence separately.

Gate A exits: if safe startup and no-tool operation work but repository review isolation does not, limit that adapter to proposal-only over deliberately supplied text snapshots. Do not count it as an isolated repository reviewer. If startup isolation itself fails, disable the automated adapter. Remaining choices are manual courier, a separately authorized API reviewer with a spending cap, or stop. No automatic paid failover or release-gate waiver. Repository review and effects remain unavailable until their required capabilities pass.
