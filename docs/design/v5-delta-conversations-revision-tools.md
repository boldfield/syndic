## 1. Open questions and corrections

**OQ-3, racing reservations.** Adopted as design: the guarantee is that a reservation and its attempt row are written in one journal transaction, and that the engine is the journal's only writer (v4 section 2a). The acceptance clause is restated as: two reservations attempted from separate goroutines released together yield exactly one dispatch and one `budget:turn`. No guarantee is required that holds without the engine's own serialization.

**OQ-4, author named as reviewer.** Adopted as design: a preset naming its author as a required reviewer is a configuration error, refused when the roster is loaded, and the engine does not start. The clause in v4 section 8 is restated as "refused at roster load". One invalid preset stops the engine; a roster is valid as a whole or not at all.

**The `quarantined` mark.** The clause added by pull request 118 is adopted: the `turn` reply marks an attempt whose late result was quarantined. It is an added reply member, which v4 section 2's invariants permit without a protocol version change. From this delta on, a change under `docs/design/` by an implementation task fails review; section 8 adds a check.

**Over-length test.** Replaced.

- The filler is the calibration text of v4 section 4a, repeated. Its size in bytes is `1.5 × assumed_context × bytes_per_token`, using the `bytes_per_token` the same probe run calibrated. When calibration is unavailable the test is recorded `not_run:no_calibration`.
- `assumed_context` comes from `--context-tokens`, else the participant's `context_tokens`, else the test is `not_run:no_context`. The fixed default of 131072 is removed.
- Each marker is a line containing 128 bits from `crypto/rand` in hexadecimal. A marker is present when its hexadecimal value appears in the reply, whatever surrounds it.
- Outcomes: `rejected:context` (the server refused the request with an explicit context-length or token-limit error, which is the wanted behaviour; the adapter classifies it from the status and the error body, and the classification rule is in the probe's export), `rejected:other` (the server refused for any other reason: authentication, quota, rate limit, content policy, an unclassified 4xx or 5xx), `accepted_whole` (both markers present), `markers_missing` (one marker or neither, with any finish reason), `errored`, `not_run:<why>`.
- Eligibility: only `rejected:context` gives `yes`. Everything else gives `unknown`: `rejected:other` says nothing about the context; `accepted_whole` says the context is larger than assumed and does not prove that the text between the markers survived; `markers_missing` is inconclusive, since a model may drop, paraphrase or decline to repeat a marker it was given in full. No outcome gives `no`: the test cannot prove silent truncation, only fail to rule it out. The export records the raw outcome and the finish reason so an operator can read the evidence.
- A participant whose eligibility is `unknown` may be a required reviewer only when its roster entry sets `accept_unknown_truncation = true`. The participants tab shows that setting. This reverses v4 section 1a's "`unknown` does not disqualify": `unknown` still does not disqualify, but accepting it becomes the operator's recorded choice per participant and not the default.

## 1a. Probing at engine start

v4 section 1a says "the engine does not probe at start", for three reasons: a probe is costly, a start-time request has the failure modes of a dispatch at every restart, and it adds nothing to the per-attempt check. The first real use showed the cost of that rule: any edit to an endpoint profile changes its fingerprint and silently invalidates its records, the operator learns of it at submit, and the remedy is to stop the engine, probe each model by hand and restart. This section replaces the rule with a narrower one.

**What is probed.** At start, after recovery has committed and the roster is validated, the engine finds every participant, and every referee model an endpoint names (section 6), with no usable record (`no_record`, `no_fingerprint` or `fingerprint_mismatch`); a referee model is probed and recorded exactly as a participant on that endpoint would be. A participant with a usable record is never probed at start, so an unchanged roster sends nothing.

**When it is automatic.** For a participant on an endpoint declared `none` or `flat`, the engine runs the probe itself. For one on an endpoint declared `metered` or `unknown`, it does so only when started with `--probe-missing`; otherwise the participant stays `unprobed` as today. A probe costs what its requests cost, and the over-length test is by construction the largest request the participant will ever receive.

**How it runs.** The engine already holds the journal lock, so it writes the probe run itself, with the same code path, raw record, export and fingerprint as `syndic probe`. Probes run one at a time. Each request has the probe's own timeout. No token budget applies to a probe, which is why an endpoint that may bill per request is probed only on the operator's flag.

**Probes are dispatches.** Every probe request goes through the capacity bookkeeping of v4 section 4: it is written as an attempt row before it is sent, it takes a slot in the endpoint's pool, a transport error that is `ErrNotSent` releases the slot and any other error leaves an uncertain-capacity hold, exactly as for a turn's attempt. Recovered holds are of two kinds, as v4 section 1b distinguishes them. An ordinary recovered hold sits on a current pool: participants in that pool are not probed and stay `unprobed` with detail `probe_failed:hold` until it is released; participants in other pools are probed. An orphaned hold has no current pool containing a member of its group, so no pool can be shown to be clear of it: while any orphaned hold exists, no start-time probe runs at all, every participant that needed one is `probe_failed:hold`, and the participants tab names the orphaned hold and the `release` that clears it. Start-time probing therefore cannot exceed a pool's capacity or hide a request whose outcome is unknown.

**Failure never stops the engine.** A probe that fails for any reason leaves the participant `unprobed` with detail `probe_failed:<reason>`, where the reason is the operational state (`unreachable`, `unauthorized`, `model_unavailable`, `hold`) or the incomplete finding below. The engine starts, and reattach, `turn`, `transcript` and recovery work as today. The engine run's manifest is written after the start-time probes, so it freezes the records they produced; nothing about the roster or the records changes during a run (v4 section 1b stands).

**Attaching during probing.** The run exists before its manifest does. The engine allocates `run_id`, emits a new event `run_opened{run_id, roster_hash}` as the run's first event, and opens the socket, all after recovery and roster validation and before any probe. `hello` keeps v4's members: `run_first_seq` is the `seq` of `run_opened`, which has been emitted, so `subscribe{since_seq: run_first_seq - 1}` replays the whole run including its probe events (a reviewer asked for the first `probe_started` here; `run_opened` is used in its place because it precedes every probe event and exists in a run that probes nothing); `manifest_hash` is `null` until the manifest is written, and `hello` gains `state: "probing" | "started"`. `engine_started` carries `manifest_hash` as in v4, so a client attached during probing learns it from the event, and `status` reports it from then on. `status`, `turn`, `transcript`, `participants` and `conversations` work during probing and report the records as they stand; `submit` is refused with `error{code: "probing"}` until `engine_started`. The manifest is written once, after the last `probe_finished`, and does not change afterwards. Nothing the client did during probing can alter the run: the run's identity is fixed at allocation, and the manifest records what the probes produced, not what any client asked. v4's acceptance clause "after a restart `hello.run_first_seq` is the `seq` of the new `engine_started` event" is restated as "of the new `run_opened` event".

**An incomplete probe is a failed probe.** A probe that captures no reported model, or finds no working max-tokens field, writes its raw record and export for diagnosis and no usable journal record. Today such a probe is recorded as usable and every later attempt fails the gate with `identity mismatch`.

**Order of events.** `engine_started` is emitted after the probes and after the manifest is written. New events `probe_started{participant}` and `probe_finished{participant, outcome, detail?}` precede it, so a client attached during a slow start can show progress.

**Surfacing.** The participants tab shows, for each participant: the record in use and its `observed_at`; or why there is none, with the failing step and the server's status in the operator's words where the probe recorded them; and the exact `syndic probe` command that would retry it. A participant probed at this start is marked `probed at start`. The banner `participants: <n> unprobed` appears while any participant in the default preset is unprobed. `submit`'s `unprobed` refusal already names the participant; the TUI shows the name and points at the tab.

**No live re-probe.** There is no socket request that probes during a run. A record changes only between runs, so the remedy for a failed probe is still to fix the cause and restart; the difference is that the restart does the probing.

## 2. Spending ceiling: deferred

Revision 1 of this draft defined a ceiling in money. It is withdrawn on the operator's direction (section 0) and belongs to a later delta. Neither milestone D nor E contains it.

**What stands, and the one change.** v2 section 6 and the v3 delta forbid dispatch to an endpoint declared `metered` while syndic has no ceiling, and the probe refuses one. Revision 2 left an endpoint that bills per token usable only under a false `unknown` declaration; both peers rejected that. The endpoint profile gains one setting:

- `spending_control = "external"`, on an endpoint declared `metered`, records that the operator bounds spend on that endpoint outside syndic (prepaid credits, a provider-side cap, an organization budget) and accepts dispatch without a ceiling in syndic. With it, the probe and the engine treat the endpoint as `flat` for admission and dispatch; the declaration stays `metered` in every record. Without it, a `metered` endpoint is refused with `spending_ceiling` exactly as today.
- The setting is recorded in the run manifest per endpoint, shown in the participants tab as `metered, external spending control`, and logged once at start. A `metered` endpoint is never probed at start without `--probe-missing`, with or without the setting (section 1a).
- This is a recorded operator acceptance, not a ceiling. It weakens v2 section 6 in the text, deliberately, in place of weakening it in practice through a false declaration.

**What bounds a turn.** `turn_max_estimated_tokens` (v4 section 4a). It covers every dispatch of the turn: each author attempt, each revision round, each tool-loop attempt of the author and of every reviewer, each referee decision (section 6), and each repair. Every one is reserved in the journal before it is sent, and a dispatch that does not fit ends the turn `budget:turn`. Sections 4 and 6 multiply the requests in a turn; they do not raise this bound.

**What does not exist.** No bound across turns, and no figure in money. The operator's bound on spend is outside syndic.

## 3. Conversations (milestone D)

**Conversation.** An ordered sequence of turns. Migration 005 adds the table `conversations{id, created_at, workspace}`, and `turns` gains `conversation_id` and `context_hash`. Every turn belongs to one conversation; turns journaled before this migration each become a conversation of one turn with `workspace` null. A null-workspace conversation is never opened by default, can be opened by `--conversation` or `/switch` from any directory, and adopts the workspace of the first submit made to it after the migration. The engine still runs one turn at a time (v4 section 3), across all conversations: while any turn is open, a submit to any conversation is refused with `busy`, as today.

**Workspace.** `submit` gains `workspace`, an absolute directory; the TUI sends its working directory. A conversation's `workspace` is set from the submit that creates it, or, for a null-workspace conversation from before the migration, from the first submit after it; once set it never changes, and a later submit with a different `workspace` is refused with `error{code: "workspace_mismatch"}`. Wherever this section matches a conversation's workspace against the current directory, a null workspace matches any directory. Milestone D stores and matches it; milestone E uses it as the root of every tool path (section 6).

**Lifetime.** A conversation has no expiry and no closed state. It can be continued as long as the journal holds it, which is until the operator deletes the journal. This delta adds no purge.

**Choosing one.** The client chooses the conversation; the engine holds no notion of a current one. On start the TUI opens the conversation for its working directory whose latest turn was submitted most recently, including a turn still running, so reattach works as in v4; if no conversation has that workspace it starts empty, as `--new` does. `syndic --new` starts with an empty conversation, created at the first submit. `syndic --conversation <id>` opens the named one and accepts any unique prefix of the id; an unknown or ambiguous prefix, or a conversation whose workspace is not the current directory, exits with code 2 and sends nothing. `syndic conversations` prints the list for the current directory and exits; `--all` prints every conversation with its workspace.

**What history contains.** For each earlier turn in the conversation that is not trimmed (below): the user's input, and then either the text the user was shown as the answer with its status, or the line `no approved answer (<state>)` for a turn that ended `incomplete` or `cancelled`. The input stays because it is the user's words and the user's later questions refer to it; the answer is withheld because text no reviewer approved and no human accepted does not become a premise for later turns. Every turn stays in the journal and the transcript.

**Labels travel with the text.** Each answer in history carries `reviewed`, `unreviewed (solo)` or `human override`; a missing answer carries its state. Author and reviewers both see the label. Participant identities are not included, so reviewer blindness (v4 section 10, point 2) holds across turns.

**Context identity.** At submit the engine renders the history once, as one canonical document, `syndic-history/v1`. The included turns are every earlier turn of the conversation from `context_from_turn` onward (all of them when it is absent), in order. For each, the document carries the fields `turn` (the id), `state`, `input`, `answer` (the text, or the missing-answer line), `label`, and, from milestone E, one `changes` field holding the change set's state and one `change` field per changed path holding `<path> applied|not applied|conflict`, that path's own outcome (section 6). Each field is written as a line `<name> <byte-length>` followed by exactly that many bytes and a newline, so the document is unambiguous whatever the content contains, and the document begins with the line `syndic-history/v1`. `context_hash` is SHA-256 over that document's bytes, frozen at submit and stored on the turn; the document itself is stored by hash so the exact history can be reproduced later. The author's message sequence and the reviewers' fenced block are both derived from the same document by a fixed, lossless rendering, so the hash binds exactly what every participant was shown, annotations included. The candidate's canonical form becomes `syndic-candidate/v2`, which adds the lines `context:<context_hash or "none">`, `round:<n>` (section 4) and `changes:<changes_hash or "none">` (section 6). An approval therefore binds to the exact history the answer was written against.

**Who receives history.** The author receives it as alternating `user` and `assistant` messages before the current input, rendered from the canonical document; a missing answer is an `assistant` message containing only the missing-answer line. Each reviewer receives the canonical document inside its `user` message as one fenced data block, delimited as v4 section 3 delimits the candidate. A reviewer cannot judge an answer to "and the second one?" without it.

**When history does not fit.** Nothing is summarized or truncated to fit (v4 section 4a stands). History counts in admission bounds and estimates as real bytes. A submit whose history does not fit a participant is refused with `error{code: "budget", budget: "context", participant, admission, limit}`. The user then starts a new conversation or trims: `submit` carries `context_from_turn`, and earlier turns are left out. The trim is the user's act, and the history document records exactly what was included. Model-written summaries are out of scope; if a later delta adds them, a summary is a candidate and goes through review.

**Protocol.** `submit` gains `workspace`, `conversation_id?` (absent creates one) and `context_from_turn?`; its reply gains `conversation_id` and `context_hash`. The request hash that v4 section 2 stores beside `submission_id` for deduplication now covers `{input, preset, quick_profile, allow_provisional, workspace, conversation_id, context_from_turn, max_rounds}` as sent, so a retry that changes any of them is `submission_conflict`, not a replay of the original reply. `status` gains `revision{default, ceiling}` for the preset in force (section 4). New requests `conversations{workspace?, cursor?, limit?}` and `conversation{id}`. The first returns, latest activity first and filtered to the workspace when one is given, `{id, created_at, workspace, last_submitted_at, turn_count, running, preview}` for each, where `preview` is the first line of the first input cut to 80 cells. The second returns the turn list with states. New event `conversation_created{conversation_id}`. `turn_submitted` gains `conversation_id`.

## 4. Revision loop (milestone D)

This implements v2 section 2's "bounded revision followed by re-review" and v2 section 4's block persistence for review mode. Solo has no loop.

**Bound.** Every turn has a round limit: the number of revisions allowed after the first candidate. A loop without one ends only when the budget or the deadline does, and an author and a reviewer who disagree do not converge. The limit is an integer from 0 to 5. Zero is the alpha's behaviour. Five is fixed in the engine and no setting raises it.

- The roster sets two values, each overridable per preset: `revision.max_rounds`, the default for a turn (default 2), and `revision.max_rounds_ceiling`, the most a client may ask for (default 5). The default may not exceed the ceiling, and the ceiling may not exceed 5; a roster that breaks either is refused at load. A default is a convenience; the ceiling is the operator's bound.
- `submit` gains `max_rounds?`, which replaces the default for that turn. A value outside 0 to the preset's ceiling is refused with `error{code: "max_rounds", ceiling}` and no turn is created.
- `syndic --rounds <n>` sets the value the TUI sends with every submit of that process. `/rounds <n>` changes it for the rest of the process, and `/rounds` alone shows the value in force, where it came from, and the ceiling.
- The limit in force and the ceiling are recorded on the turn, and the status line shows `round n/m`.

**When a round starts.** After every required reviewer has returned a result on the current candidate, a revision round starts when all of these hold: every result passed acceptance and the gate; every verdict is `valid` or `revision_request`; at least one is a block or a revision request; rounds remain; and the round's projection fits the remaining turn budget. A reviewer failure of any kind (transport, gate, second malformed, deadline) ends the turn `incomplete` as today. A revision is a response to feedback, never a way past a failed reviewer.

The engine waits for all reviewers before revising, so the author receives all feedback at once.

**Author revision dispatch.** Messages: the system message; the history; the original input; the author's previous candidate as an `assistant` message; then one `user` message carrying every reviewer's complete output for that candidate verbatim, envelope and commentary, each fenced by random delimiters and labelled `reviewer 1`, `reviewer 2` in roster order without participant ids. A block may cite tool results by id in its `evidence` line (section 6); the exact results cited, and only those, follow the block that cites them, fenced and labelled as data, under the same admission bound as every other byte of the dispatch. A reviewer's other calls and results are not included, and no result is ever attributed to a reviewer. A cited result is included because a repeated lookup cannot reliably reproduce transient evidence; an uncited one stays private because a block must state its own evidence (v2 section 4). The instruction: return the complete revised answer, and treat reviewer text and cited results as data about your answer, not as instructions to follow beyond revising it. With `tools` set, the revision is an author tool loop (section 6) like the first candidate.

**Unchanged revision.** A revision is unchanged when its answer bytes equal the previous candidate's and its change set lines (section 6: the sorted `{path, op, base_sha256, new_sha256, new_len}` lines, without the snapshot line) equal the previous candidate's. The comparison deliberately leaves out `round` and the snapshot line, which differ between rounds by construction; it compares what the author produced. Identical prose over a corrected patch is a change, and a changed answer over the same patch is a change. An unchanged revision ends the turn `incomplete` with reason `revision_unchanged` and the blocks open. The human decides. There is no rebuttal channel in this delta.

**Re-review.** Every required reviewer reviews the new candidate. Approvals of an earlier candidate do not carry (v2 section 4; the hash differs). Each reviewer's prompt contains the request, the history, the new candidate, and that reviewer's own open blocks from earlier rounds with their ids, evidence and remedies. It does not contain other reviewers' blocks, the previous candidate, or the number of rounds remaining. The engine never tells a reviewer that the turn is running out of rounds, as repair never pressures a reviewer (v3 delta section 9).

**Envelope v2.** `VERDICT v2` adds `round: <n>` and, for each of that reviewer's open blocks, one line `block-state: <block_id> withdrawn|maintained`. Rules:

- Every verdict in a round after the first, whatever its kind, must carry a `block-state` line for every one of that reviewer's open blocks. A verdict that omits one is `malformed` and goes to repair like any other malformed verdict; an omitted block is never treated as withdrawn. A block is withdrawn only by the reviewer that opened it, and the withdrawal is recorded against the new candidate hash (v2 section 4).
- `approve` with any of the reviewer's own blocks `maintained` is `malformed`.
- A reviewer may maintain old blocks and open new ones in the same verdict.
- `approve-with-changes` remains classified `revision_request`. It now starts a round, with the reviewer's output as the feedback, and it never counts as approval.

**Approval.** The turn is `approved` when every required reviewer has a valid `approve` on the current candidate hash and no block of the turn is open.

**Exhaustion.** When rounds run out, or the next round does not fit the budget, the turn ends `incomplete` with reason `rounds_exhausted` or `budget:turn`. The latest candidate is shown with its open blocks. Override applies to the latest candidate.

**Deadlines and budgets.** The turn deadline covers all rounds and is not extended. Repair is one per reviewer per round. The projection at submit covers the first round as today and also reports the worst case across all rounds, labelled as such; it refuses only on the first round. Every later dispatch is checked by reservation as today.

**State machine.** After `reviewers_dispatched`: `→ revision_dispatched (round n) → candidate_frozen (round n) → reviewers_dispatched`. The epoch is bumped when a round starts. `candidates` gains `round` and `supersedes`; `turns.candidate_id` names the latest. New terminal reasons: `rounds_exhausted`, `revision_unchanged`. `all_approved` is unchanged; the turn record carries the round count.

**Terminal delivery.** Once, at the terminal state, carrying the final round's reviewer outputs and every block with its final state.

**What this does not claim.** A loop makes approval more likely. It does not make an approved answer more likely to be correct, and a reviewer may withdraw a sound block under repetition. The answer shows how many revisions preceded approval, and the transcript shows every round.

## 5. TUI (milestone D)

v4 section 7 stands except as changed here.

**Layout.** Top to bottom: tab bar, one line; the active tab; banners, when any apply; the input, one or more lines; the status line, one line, at the bottom. The status line carries what v4's strip carried, plus `round n/m` during a revision, and at its right edge the key hint `tab: switch  /help`.

**Tabs.** `chat`, `transcript`, `participants`. Milestone E adds `changes`. The `answer` tab is replaced by `chat`.

**Chat tab.** The conversation, scrolling, oldest at the top. Each turn shows the user's input and then its outcome. Every banner and label of v4's answer tab is kept word for word: the `approved by <ids> against <hash prefix>` line, `UNREVIEWED (solo)`, `INCOMPLETE, not approved`, `HUMAN OVERRIDE: <reason>`, `CANCELLED, not approved`, and the red `UNREVIEWED DRAFT` for drafts. An approved answer reached by revision reads `approved by <ids> after <n> revisions against <hash prefix>`. While a turn runs, the chat shows one progress line: phase, round, participant states, elapsed time. A turn that ended `incomplete` or `cancelled` shows its outcome banner and, below it, the line later turns see in its place, `no approved answer (<state>)` (section 3). Turns dropped by `/trim` are shown dimmed with the marker `not in context`.

**No streaming.** Requests stay non-streaming (v3 addendum section 3). Reviewed text cannot be shown before review without the draft banner, so there is nothing to stream in the default mode.

**Keys.** `Tab` and `Shift+Tab` switch tabs, as today. `PgUp` and `PgDn` scroll the active tab. `Ctrl+D` on an empty input detaches, exactly as `/quit`. `Ctrl+C` clears a non-empty input; on an empty input it detaches. Neither ever cancels a turn: v4's invariant that detach never cancels stands, and `/cancel` remains the only cancel. `Alt+Enter` inserts a newline; a multi-line paste is kept as typed.

**Commands added.** `/help` (commands and keys), `/new` (start a conversation), `/conversations` (the list of section 3: id prefix, last activity, turn count, preview, with the open one marked), `/switch <id>` (any unique prefix; refused for a conversation whose workspace is not the current directory, as `--conversation` is), `/trim <turn>` (sets `context_from_turn` for later submits in this conversation, after showing what is dropped), `/rounds [n]` (section 4), `/budget` (tokens reserved, charged and the limit; v2 section 7 names this command).

**Start-up flags.** `--new`, `--conversation <id>` (section 3) and `--rounds <n>` (section 4). `--new` and `--conversation` together exit with code 2. The chat tab's first line names the open conversation by id prefix and turn count, so the user can see which one was opened by default.

**Switching while a turn runs.** `/new` and `/switch` are allowed. They change what the chat tab shows and where the next submit goes; the running turn continues, and a submit made before it ends is refused with `busy` (section 3), and the TUI names the conversation the open turn belongs to.

**Plain terminal.** v4's rules stand. At 80×24 the tab bar, at least five lines of the active tab, the input and the status line all fit.

## 6. Tools (milestone E)

**Scope.** Engine-executed tools for the author and for reviewers. The author may read, fetch and stage writes. A reviewer may read and fetch, and never writes: one participant produces the change set and the others judge it. A reviewer without tools can judge a factual claim only by how plausible it reads; with them it can check the claim against a source of its own choosing. No shell, no command execution, no MCP: those need per-call authorization or an OS sandbox (v2 section 8), and each is a later delta.

**Who executes.** The engine, never the adapter, so v3 delta section 3's rule stands: the adapter returns tool calls as data. `CompleteRequest` gains `Tools` and `tool` role messages; `CompleteResult` gains `ToolCalls`. The dialect is Chat Completions `tools`, `tool_calls` and `role: "tool"`. Several calls in one result are executed one at a time, in the order returned.

**Probe.** A new probe step sends one request with one harmless tool and records `tool_calls: yes|no|unknown`. A participant not recorded `yes` cannot hold a role that the preset gives tools; `submit` refuses with `preset_invalid` and detail `no_tool_calls:<id>`.

**Enabling.** Two preset fields, both default empty. `tools`, a subset of `["read", "web", "write"]`, is the author's set. `reviewer_tools`, a subset of `["read", "web"]`, is every required reviewer's set; naming `write` there is invalid at roster load. The two are independent: reviewers may have tools when the author has none. `write` requires `mode = "review"`; a solo preset naming it is invalid at roster load (v2 section 5).

**The tools.**

- `read`: `read_file{path, offset?, limit?}`, `list_dir{path}`, `search_files{pattern, path?}`.
- `web`: `web_fetch{url}`; and `web_search{query}` only when the roster configures a search provider under `[tools.web.search]` with a secret reference. With no provider the tool is not offered.
- `write`: `write_file{path, content}`, `edit_file{path, old, new}`, `unstage{path}`. `unstage` removes the path from the turn's staging map, so a revision can retract a proposed creation or change; the path reads as its base again. No delete of workspace files in this delta.

**Tool steps are results.** A result is a tool step when its transport finish status is the dialect's tool-call finish (`tool_calls` in Chat Completions) and it carries at least one call. A result that carries calls under any other finish status is not a tool step: `length` is a truncated result and fails acceptance as today, a content-filter or refusal finish fails acceptance as today, and `stop` with calls attached is malformed. A tool step is accepted before anything is executed, under the same checks as every other attempt result in v4 section 4: identity, current epoch, the attempt's own completion; a late or quarantined tool step is journaled and never executed. Each call in an accepted step is then checked in order: the tool must be one the caller's role is given in this preset, the arguments must parse and validate against the tool's schema, and the caller must have calls remaining under its bound. A call that fails a check is answered with a tool error and journaled; the remaining calls are still checked and run. Acceptance of the step is not acceptance of its effects: immediately before each call's effect (the observation, the staging write, the network request), and again after any wait inside it, including a referee decision, the engine re-checks that the turn is open, not cancelled, and that the attempt's epoch is current; a call that fails the re-check is journaled `abandoned` and has no effect, and the attempt ends as the cancellation or epoch change dictates. The attempt status set gains `tool_step`, with the transition `tool_step → executing → next attempt`; today a result carrying `tool_calls` maps to an error status, and that mapping is removed.

**Workspace and confinement.** The workspace is the conversation's (section 3). Confinement is enforced on the opened file, not on the path string: the engine opens the workspace root once per turn, walks each requested path one component at a time relative to that root with `openat` and `O_NOFOLLOW`, refuses any component that is a symbolic link or that leaves the root (`..`, an absolute component), and reads, stats and writes through the descriptor it obtained. The same walk is used by `apply` for its temporary file and rename. A path that is swapped for a link between check and use therefore fails at open, not after. `tools.protected_paths` lists patterns no tool may read or write; the default covers `.git/`, `.syndic/`, `.env*`, private-key file names and the syndic configuration and state directories, and the check runs on the resolved relative path. This is confinement inside the engine process, not a sandbox. It is sufficient only because no tool runs a program; a tool that does needs v2 section 8's enforcement.

**Snapshot.** A turn's tools observe a record of observations, not the live tree, so that every participant sees the same state and every diff can be reconstructed. It is a set of recorded observations acquired at different times during the turn, not a complete point-in-time picture of the filesystem, and nothing in this design claims otherwise. An observation is one of: a file's content (stored in the content-addressed store, recorded with `base_sha256`); a path's absence; a directory's entry list (names and types, stored). The first time any tool of any participant observes a path or directory, the engine takes the observation from the live tree and records it; every later observation of it, by any participant, in any round, is served from the record. `read_file`, `write_file` and `edit_file` observe the file; `list_dir` observes the directory; `search_files` first observes, through the same mechanism, every directory in its scope and every file it must open, so a repeated search over the same scope sees the same tree. Observations are taken under one lock per turn, so two first touches of the same path by concurrent reviewers yield one record and one reader of the live tree. The record is one namespace, and a later observation never contradicts an earlier one. A recorded directory listing fixes which names exist in that directory: a name not in it is absent for the rest of the turn, and a later `read_file` of such a name is answered `not found` from the record even if the live tree has since gained the file. A recorded absence is honoured the other way: when its parent directory is listed later, the live listing is taken and that name is removed from it before it is recorded. A name a listing recorded as present, whose content has not yet been observed, has its content taken from the live tree at first read; if the live file is gone or has changed type by then, the observations conflict, nothing is recorded, the call returns the tool error `snapshot_conflict` naming the path, the conflict is journaled, and the turn continues. A file whose content is recorded and whose parent is listed later appears in that listing whatever the live tree says. Staged changes are an overlay on the record, not part of it, and every tool sees the same overlay: a staged creation appears in `list_dir` and is searched by `search_files`; a staged edit is what `read_file` returns and what `search_files` searches; `unstage` removes the overlay entry and the recorded base shows again. The record is versioned: every observation appends to it and bumps `snapshot_version`, journaled with the observation and the attempt that made it. Its canonical form is length-framed, as the history document's is, because names may contain any byte including a newline: each record is a line `<kind> <path-byte-length>` (`f`, `a` or `d`), then exactly that many bytes of path and a newline, then the value line (`base_sha256`, empty, or `entries_sha256`); an entry list is hashed over its names sorted bytewise, each written as a line `<type> <name-byte-length>` followed by the name's bytes and a newline. `snapshot_hash` is SHA-256 over the records sorted bytewise by path, at candidate freeze, and is part of the candidate (below), so the candidate binds every observation the author's work rested on, at the version frozen with it. An observation after freeze, by a reviewer's first touch, extends the record to a new version; it is bound to that reviewer's verdict (the verdict record carries the version it saw and the observations it added, beside the tool results it received), and every later observation of the same path in the turn is served from it. A candidate can depend on files its author never read: generated code calls into them. That is what a reviewer's reads are for, and it is why a post-freeze observation is neither refused nor a trigger for re-review: the reviewer that made it judged the candidate with it in view, the evidence is immutable and versioned, and refusing it would leave a reviewer able to check a candidate only against what the author chose to read. A later round's author sees the extended record, and its new candidate freezes the version it rested on. The live tree is consulted again only by `apply`.

**Egress of file-derived content.** File-derived content is anything that carries workspace bytes to a model: a `read` result, a staged write's content or an `edit_file` argument, a base content or a diff given as evidence, a change set, and the answer and `change` fields of any file-tainted turn in a later turn's history. A turn is **file-tainted** when it ran with `read` or `write` for any role, or when any earlier turn of its conversation is file-tainted. Taint is therefore transitive and conversation-wide: an answer written with a tainted answer in view can reproduce its bytes, and later answers can reproduce that one. It is computed at submit from the journal's record of the conversation's turns, not from the history the submit includes, and recorded on the turn (`file_tainted`); `context_from_turn` cannot clear it, so trimming the first tainted turn out of view does not launder the answers written after it. The rule: any role that could receive file-derived content must be on an endpoint with local execution or one named in `tools.file_egress_destinations`. In a preset that gives any participant `read` or `write`, that is every participant, because diffs and change sets go to every reviewer and history goes to everyone; such a preset is refused at roster load when any participant fails the rule, naming the participant and the route. A tainted conversation carries the rule forward: a submit to it under a preset whose participants do not all satisfy the rule is refused with `error{code: "egress", route: "history", participant}`, whatever tools that preset grants and wherever the trim is set. The check is on routes, not on the configured `read` permission alone.

**Egress of lookups.** Whatever an author's tool returns is sent to the author's endpoint and then, as evidence, to every reviewer's endpoint. Whatever a reviewer's tool returns is sent to that reviewer's endpoint only.

**Public web egress.** `web_fetch` sends `GET` requests chosen by a model to hosts on the public internet. Permitting that from the author and reviewers is an operator-authorized replacement of v2 section 8's prohibition on arbitrary tool egress, recorded here, not a reading of it. The scheme and address rules: a URL whose scheme is not `http` or `https` is refused before anything else; after the pre-send checks and the referee have allowed the URL, and not before, the engine resolves the hostname, refuses the fetch if any resolved address is loopback, link-local, private (RFC 1918 and unique-local), multicast, unspecified or an IPv4-mapped form of one of those, and otherwise connects to the exact address that passed, never to a fresh resolution. The same rules run for every redirect target. What the engine does between the scheme rule and resolution is the subject of the headings "Pre-send checks" and "Referee" below.

**Web with file content.** Allowed by default; the operator can turn it off. This is the operator's direction, and it is the one place in this delta where the default is the less safe choice, so it is stated at length. One reviewer dissents from the default and the dissent is recorded (section 10).

- The risk. A participant that can fetch and also holds file content can be told, by text in a page it fetched, to put that content into the URL of a later fetch. The page's owner then has it. The model does not need to be compromised, only to follow text it was told is data.
- Who is exposed. Any participant with `web` that receives file-derived content by any route above. An author with `read` and reviewers with `web` is the ordinary coding preset, and it is exposed.
- What can leak. Anything a tool can read: files inside the workspace that match no protected pattern. Files matching `tools.protected_paths` cannot be read and so cannot leak this way. Source code, documents and any secret in a file the patterns miss can leak.
- What stands between the model and the network. Two layers, below, run before every fetch and every search is sent: deterministic checks, then a referee. Both are heuristics that reduce exposure. Neither is prevention. The deterministic layer refuses the loud cases: a URL that carries bytes the model has seen, an oversized or high-entropy value, too many fetches. The referee refuses requests that do not fit the user's ask, and does not do so reliably. Neither stops a patient attacker who moves plausible-looking data a few bytes at a time through URLs that resemble ordinary documentation paths, within the caps. Every fetch and every refusal is journaled with its full URL, and the transcript shows them, so what did happen is visible afterwards.
- How to turn it off. `tools.allow_web_with_read = false` on the roster, or per preset. A preset in which any participant has `web` and any participant has `read` or `write` is then refused at roster load, naming the participants; and a submit under a preset with `web` to a tainted conversation is refused with `error{code: "egress", route: "history", participant}`, the same carry-forward as the destinations rule above. A preset whose only tool anywhere is `web`, in an untainted conversation, is unaffected. This remains the stronger setting.
- Where it is stated. The roster reference documents the setting with the risk and the limits in the words above. The example roster shows both settings, with a comment. For every preset where the combination is in effect, the participants tab shows `web + file content: allowed, pre-send checks + referee` and names the exposed participants, and the engine logs one line saying so at start. The run manifest records the setting.

**Pre-send checks.** Deterministic, no model, applied to every `web_fetch` URL and every `web_search` query from every role. The order is fixed, because a DNS query is itself network activity that carries the hostname: first the scheme rule on the URL string; then the checks below and the referee, all on the URL string and with no name resolution; only after an allow does the engine resolve the hostname, apply the address rule, and connect to the validated address. The constants are design constants; the acceptance tests fix them.

1. Canary. The engine keeps, for the turn, every file-derived byte sequence any participant has been exposed to: snapshot contents read, staged writes, base contents of staged paths, the diffs given as evidence, and the `answer` and `change` fields of the history document (not its `input` fields, which are the user's own words and may contain URLs the user pasted). A URL is refused if, after percent-decoding, and after bounded decoding of each hostname label, path segment and query value (base64, base64url and hex, each alone and any one nested once inside any one, itself included, so base64-of-hex, hex-of-base64 and base64-of-base64 are decoded and a third level is not), it contains any run of at least 16 bytes that occurs in that set. Hostname labels are checked because a name is sent to a resolver before anything else. Sixteen is below the length of most secrets and identifiers worth exfiltrating and above the length of common path words.
2. Shape. A URL longer than 2048 bytes is refused. A hostname longer than 253 bytes or with a label longer than 63 bytes is refused. A single hostname label, path segment or query value longer than 48 bytes whose Shannon entropy exceeds 4.5 bits per byte is refused. The eleventh fetch to one host in a turn is refused. The fetch after `tools.max_fetches_per_turn` (default 20, counted across roles and hosts) is refused.
3. Redirects. A redirect is not followed by the HTTP client. Each redirect target is a new URL and goes through the whole sequence again: scheme rule, these checks, the referee, then resolution, address rule and a pinned connection; after three hops the fetch is refused. A redirect to a different host is not followed at all: the tool returns the target URL as its result and the model may fetch it as a new call.
4. `GET` only, no cookies, no credentials, no body.
5. `tools.web.allowed_hosts`. When set, an allowlist checked on the canonical hostname: lowercase, punycode, default port stripped. An exact host matches itself only; `*.example.com` matches subdomains and not the apex; `**.example.com` matches both. There is no suffix matching. IP literals are refused whenever an allowlist is set.
6. `web_search`. Not offered unless the provider's host would pass these checks and the allowlist when one is set; the query is checked by the canary and shape rules exactly as a URL is, and goes to the referee; the provider's hostname is resolved only after the query is allowed, under the same address rule and pinning as a fetch. The provider receives the query whatever else is set, and the roster reference says so.

Every refusal is journaled with the rule that fired and the full URL, and the model receives a tool error naming the rule.

**Referee.** A model that answers one question per `web_fetch` or `web_search` that passed the checks above: allow or deny. It is a roster role, `referee`, not a reviewer; it casts no vote on any candidate.

- Endpoint. The referee for a call runs on the calling participant's own endpoint, or on an endpoint with local execution. Any other endpoint is refused at roster load, naming the referee. A reviewer's calls are therefore refereed on that reviewer's endpoint and the author's on the author's, and no participant's bytes reach another participant's endpoint through the referee. A cross-endpoint referee is not in this delta; if one is ever added it is an explicit, narrow exception with per-field authorization of the payload.
- Model. Each endpoint profile that any participant with `web` uses names its referee explicitly in the endpoint's `[endpoints.<name>]` table: `referee_model = "..."`, run on that same endpoint, and optionally `referee_endpoint = "<name>"`, which must name an endpoint with local execution and moves the referee for that endpoint's callers there. These two fields are the whole configuration of the `referee` role; naming a `referee_endpoint` without local execution is refused at load. There is no default and no "cheapest" rule; a roster that grants `web` to a participant whose endpoint names no referee model is refused at load, naming the endpoint. On a local endpoint the operator names any model it serves. The referee model is probed like a participant, through the same probe path and the same records: `syndic probe` probes it with the endpoint's participants, section 1a's start-time probing covers it, and it needs a usable record and need not support tool calls. A referee model with no usable record leaves every `web` tool on that endpoint unoffered for the run, and the participants tab says why.
- Payload. The complete payload is: the user's input for the turn; the proposed call's name and URL, or query; the caller's own earlier `web_fetch` and `web_search` calls this turn, as name and URL only. Nothing else: no tool result, no fetched content, no candidate text, no argument of `read_file`, `write_file`, `edit_file` or `unstage`, no other participant's calls. The prompt is a fixed engine template whose hash is in the run manifest, and the acceptance test asserts the rendered payload byte for byte.
- Output. `allow` or `deny` with one line of reason. The request's `MaxOutputTokens` is `tools.referee.max_output_tokens`, default 64, and the reservation uses it. Any other outcome of a dispatched referee request, a timeout, an adapter error, a provider-side refusal, a malformed reply, a reply carrying tool calls, a reply cut off at the bound, is a deny. A referee dispatch that cannot be reserved because the turn budget is exhausted is not a deny: it is a reservation failure and ends the turn `budget:turn`, as v4 section 4a requires for any dispatch.
- Acceptance. An `allow` authorizes the fetch only when the referee result passes the same identity, epoch and completion checks as any attempt result under v4; a late or quarantined referee result authorizes nothing.
- Fail closed, for the call. A deny returns a tool error to the calling model and the calling attempt continues where v4 permits. The referee never decides to end a turn, and it does not exempt the turn from v4: cancellation, the turn and attempt deadlines, budget exhaustion and uncertain-capacity holds still govern, and a referee dispatch on the caller's shared pool can itself consume capacity or hit a hold.
- Order. The deterministic checks run first; the referee is consulted only for a URL that passed them, and for every redirect hop; name resolution happens only after the referee allows.
- Accounting. Each referee decision is a dispatch: reserved in `BeginAttempt` with its complete request in admission, charged, reconciled and quarantined on lateness exactly as any attempt under v4 section 4a. It is journaled as `referee_decision{call_id, attempt_id, verdict, reason_sha256}` with the reason text in the content store. The transcript shows the decision under the tool call, and the chat progress line shows `referee: deny` when it fires.
- Manifest. Per endpoint: the referee model, its probe record and the template hash, beside the `allow_web_with_read` setting.
- `metered`. The v4 refusal and section 2's recorded acceptance apply to the referee exactly as to any other dispatch on that endpoint.
- Implementation. The endpoint referee is one implementation of a `Referee` interface; the fake adapter scripts it in tests. An embedded, purpose-trained referee is a later delta and fits behind the same interface.

**Admission with tools.** v4 section 4a's admission bound and reservation are computed over the rendered request. With tools that request also contains the tool definitions and their schemas, every earlier `assistant` message's tool-call arguments, every `tool` message's framing (delimiters, labels, the untrusted-content notice) and content, and, for the referee, its whole template. All of it counts as prompt bytes in the bound and in the reservation; nothing in a tool request is estimated outside the formulas. The acceptance test renders a request with definitions and results and checks the reservation against the rendered size.

**Author tool loop.** With `tools` set, the author phase of a round is a sequence of author attempts. An attempt that returns tool calls is followed by execution and a further attempt carrying the results. Every attempt is reserved, gated and charged like any dispatch. Bounds: `tools.max_calls_per_turn` (default 20), the turn deadline, the turn budget. A result larger than `tools.max_result_bytes` (default 65536) is not truncated: the model receives an error stating the size, and for a file may ask for a range. When the author reaches the call bound, its next attempt is sent without tool definitions and with the statement that no further tool calls are available, exactly as for a reviewer below; a result of that attempt that carries tool calls ends the turn `incomplete` with reason `tool_limit`, and one that carries none is the candidate.

**Reviewer tool loop.** With `reviewer_tools` set, each reviewer's review of a candidate is a sequence of that reviewer's attempts.

- A result that carries tool calls is a tool step (above), whatever text accompanies it; the text is journaled and not parsed. A result that carries none is the verdict and goes through acceptance, the gate and repair exactly as today.
- Each reviewer has its own bound per round, `tools.max_reviewer_calls` (default 10). When a reviewer reaches it, its next attempt is sent without tool definitions and with the statement that no further lookups are available. Tool calls in the reply to that attempt are a reviewer failure. Nothing in that statement asks for approval; a reviewer that could not verify a claim can block on it.
- Reviewers' loops run concurrently, as their single attempts do today. The attempt deadline applies to each attempt and the turn deadline to all of them.
- A reviewer's `read` sees the snapshot with the candidate's staged changes applied, as the author's does. The diff it is given shows the base.
- No reviewer sees another reviewer's calls or results, in any round. The author sees only the results a block cites, in a revision round (section 4).
- A repair attempt carries the reviewer's earlier tool results and no tool definitions.

**Results are data.** Each result is given to the model fenced by random delimiters and labelled as untrusted content. Each call and result is journaled and stored by content hash: `tool_calls{id, attempt_id, name, args_sha256, class, status}` with the result's `sha256` and `byte_len`. The attempt identifies whose call it was.

**Verdict evidence.** A verdict's record carries the ids of the tool results that reviewer received before giving it. A block's `evidence` line may cite any of them by id; the cited results are the only ones a revision round carries to the author (section 4). They are not part of the candidate hash: the candidate is what the author produced. The transcript tab shows each reviewer's calls and results under its verdict, and the chat tab's approval line is followed by `checked with <n> lookups` when any reviewer made one.

**What reviewer tools do not claim.** A fetched page can mislead a reviewer as it can an author, and can carry text written to produce an approval. When the author and a reviewer fetch the same page, their agreement is one source counted twice. Labelling results as data lowers that risk and does not remove it. What this design gives the human is the record: every source behind every verdict, in the transcript.

**Staged writes.** `write_file` and `edit_file` never touch the workspace. The engine keeps a staging map for the turn, path to new content hash, with the content in the content-addressed store. A read in the same turn sees staged content over the snapshot. The first time a path is staged its base is taken from the snapshot, or snapshotted at that moment, so `base_sha256` is the hash of the stored base content, or `absent`. `unstage` removes the entry. Staging persists across revision rounds.

**Change set.** At candidate freeze, the change set is the list, sorted by path, of `{path, op: create|modify, base_sha256, new_sha256, new_len}`. `changes_hash` is SHA-256 over its canonical lines followed by the line `snapshot:<snapshot_hash>`, and is part of the candidate (section 3); a candidate therefore binds both what it changes and the base it was written against. The candidate's `evidence` line, unused until now, carries `<call_id>:<result_sha256>` for each of the turn's author tool results in order, so a changed result changes the candidate hash.

**What reviewers receive.** The request, the history, the candidate text, the change set as unified diffs the engine generates from the stored base contents (full content for a created file), and every author tool call with its result verbatim, fenced and labelled as data. Because bases are stored, the same diff can be regenerated from the journal at any later time. If that does not fit a reviewer's context the turn ends `incomplete` with `budget:context:<reviewer>`. Nothing is summarized. A reviewer's own lookups add to its context after that; one that no longer fits is a reviewer failure with the same reason.

**Apply.** Approval does not write files. It makes the change set appliable. `apply{turn_id}` is accepted for a turn that is `approved` or `overridden` and has a change set, and the TUI sends it on `/apply` after showing the diff.

- Change-set state and per-path outcome. A change set is in one of `appliable`, `applied`, `partial`, `conflict` or `discarded`. Separately, every path in it carries its own outcome, `pending`, `applied` or `conflict`, set by classification and by each `apply_file`, and never rewritten by a later state change. Both are journaled and shown in the `changes` tab. History carries both: one `changes` field with the change set's state, and one `change` field per path with that path's outcome (`applied`, `not applied` for `pending`, `conflict`), so a change set discarded after a partial apply still shows which files were changed.
- Exclusive access. An apply has the exclusivity of a turn: the engine runs one turn or one apply at a time, so `apply` is refused `busy` while a turn or another apply is open and `submit` is refused `busy` while an apply runs; the `busy` error names which. No turn therefore observes a half-applied tree. The workspace root is opened once at the start of the apply and every operation is relative to that descriptor, so a workspace directory renamed or moved during the apply is followed, not lost; a root that cannot be opened returns `error{code: "workspace_missing"}` and nothing is written. The engine does not and cannot lock out other processes: the contract is that it writes a path only after re-verifying, by re-opening the target by name immediately before the rename (below), that what the name refers to still hashes to the base; an edit landing in the interval between that check and the rename is overwritten, and the design states this as the residual window rather than claiming atomicity it does not have.
- Classification. The engine first classifies every path from the live workspace, through the confined open above: at its `base_sha256`, pending; at its `new_sha256`, done; at neither, `conflict`. On a first apply every path must be pending; any that is not returns `error{code: "base_changed", paths}`, the change set stays `appliable`, and nothing is written.
- Writing. It journals `apply_started{turn_id, paths, new_sha256s}`, then for each pending path: writes the content to a temporary name in the target's directory through the confined open; then, immediately before replacing, re-opens the target by name through that directory's verified descriptor (`openat` with `O_NOFOLLOW`, never a descriptor kept from classification, which after an editor's atomic save would still name the old inode while the path names newer content), and checks that what the name now refers to is a regular file whose content hashes to the base; then renames the temporary file over it and journals `apply_file{path, new_sha256}`. A path whose base is `absent` is created without replacement: the temporary file is linked to the name with an operation that fails if the name exists (`linkat`, or `renameat2` with `RENAME_NOREPLACE`), and an existing name is a `conflict`. A target that fails the re-check is a `conflict` and is not written. After the last path, `apply_finished{state}`. A rename is atomic per file; the set is not atomic; the interval between the re-check and the rename remains the stated residual window.
- Retry and recovery. `apply` on a change set that is `applied` returns `{state: "applied"}` and writes nothing. A change set is `partial` when the journal holds its `apply_started` with no `apply_finished`, and `conflict` when a finished apply left at least one path at neither hash. On a `partial` or `conflict` change set, done paths are skipped, pending paths are written, and any `conflict` is reported by name after the pending ones are written; the state becomes `applied` when every path is done, else `conflict`, and the journal records which. Recovery after a crash classifies every path of an unfinished apply, records the state, and reports it; it writes nothing on its own. `apply` is therefore idempotent and a partial apply is reported file by file rather than guessed at.
- `discard{turn_id}` moves an `appliable`, `partial` or `conflict` change set to `discarded`. It changes no per-path outcome and deletes nothing: the paths already applied stay recorded as `applied`, and the change set, its base contents and its diffs remain in the journal as the evidence the reviewers saw. The `changes` tab and later history show a discarded change set with its per-path outcomes.
- A change set is never dropped because a later turn staged the same path. Two change sets touching one path are both appliable until one is applied; the other then fails the base check, which is the right answer. Applying marks the change set `applied` and preserves it.
- An applied override is recorded as applied under human override.

**History.** A later turn's history contains the answer text and the change set's state and one line per changed path with that path's own outcome (`applied`, `not applied` or `conflict`), inside the canonical history document so the lines are under `context_hash` (section 3). Tool results are not carried forward.

**TUI.** The `changes` tab shows the staged diff, the base check result, and applied state. During a turn the chat's progress line shows each tool call as one line: role, name, target, status, and `referee: deny` when the referee refuses one. A reviewer's line names it `reviewer 1` or `reviewer 2`, as elsewhere. Commands `/apply` and `/discard`.
